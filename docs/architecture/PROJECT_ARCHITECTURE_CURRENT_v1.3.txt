7. PHASE 5C — HUMAN HANDOFF NOTIFICATION
======================================================================

New human_handoffs transactionally create:

event_type:
HUMAN_HANDOFF_REQUESTED

The handoff row and outbox event are created in the same PostgreSQL
transaction.

Current worker:

P5 — Human Handoff Notification Worker

Flow:

Schedule / Manual Trigger
→ Worker Context
→ claim HUMAN_HANDOFF_REQUESTED
→ load authoritative handoff details
→ build operator notification
→ SMTP operator email
→ complete outbox event

Failure path:

SMTP/error
→ fail_outbox_event_v1
→ FAILED
→ delayed retry
→ eventual retry or DEAD_LETTER

Verified behavior:

- successful email delivery;
- FAILED after controlled notification failure;
- delayed retry;
- later successful delivery;
- final PROCESSED state;
- cleared worker lock;
- cleared last_error after success.

Notification delivery is at-least-once.

A crash after SMTP acceptance but before outbox completion may result in a
duplicate operator email after lease recovery.

This is accepted current behavior.

8. PHASE 5D — DEAD-LETTER ALERTING
======================================================================

Migration:

20260911202903_outbox_dead_letter_alert.sql

When a non-alert outbox event transitions to:

DEAD_LETTER

PostgreSQL transactionally creates exactly one:

OUTBOX_DEAD_LETTER_ALERT

The generated alert preserves:

- original outbox event ID;
- original event key;
- original event type;
- original aggregate;
- attempts;
- maximum attempts;
- last error;
- dead-letter timestamp;
- correlation ID.

Current worker:

P5D — Dead-Letter Operator Alert Worker

Flow:

Schedule / Manual Trigger
→ claim OUTBOX_DEAD_LETTER_ALERT
→ build operator alert
→ SMTP operator email
→ complete alert outbox event

A dead-letter alert that itself reaches DEAD_LETTER does NOT generate another
dead-letter alert.

The recursion guard has been explicitly tested.

Verified:

recursive_alert_count = 0

12. PHASE 6 TELEPHONY DIRECTION
======================================================================

Preferred integration:

AUSTRALIAN PSTN
→ TWILIO NUMBER
→ TWILIO ELASTIC SIP TRUNK
→ RETELL

Use Retell custom telephony through Elastic SIP Trunking.

Do not use the Dial-to-SIP integration unless a verified requirement makes
Elastic SIP Trunking unsuitable.

Reason:

Elastic SIP Trunking preserves Retell telephony capabilities including native
call-transfer support.

Dial-to-SIP would require custom transfer implementation and would unnecessarily
expand the backend.

Current Phase 6 architecture must remain:

Twilio = PSTN / SMS transport
Retell = voice agent and transfer execution
PostgreSQL = authoritative state
Edge Functions = verified provider ingress / synchronous controls
n8n = asynchronous missed-call recovery and notification orchestration
