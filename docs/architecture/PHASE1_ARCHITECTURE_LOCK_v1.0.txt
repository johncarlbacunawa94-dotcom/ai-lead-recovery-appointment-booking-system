======================================================================
1. LOCKED PLATFORM DECISIONS
======================================================================

VOICE AI
- Retell AI
- Use Conversation Flow.
- Initial implementation should use rigid/controlled flow behavior rather than an oversized single prompt.
- Web calls are used first.
- Do not buy a phone number during the initial voice foundation.
- Vapi remains the strongest alternative, but Retell is the selected platform for this project.

DATABASE / DEMO CRM
- Supabase-managed PostgreSQL.
- PostgreSQL is the authoritative system of record.
- Supabase is the development/hosting platform around PostgreSQL.
- Do not make n8n Data Tables the authoritative business database.

APPLICATION / BACKEND SERVICE
- Use application-service modules, initially exposed through Supabase Edge Functions where appropriate.
- This layer owns synchronous tool APIs and deterministic business controls.
- Keep the business-service code portable enough that it could later move to an always-on Node/TypeScript service if real-time latency testing proves that necessary.
- Do not make that change casually; it requires a verified reason.

ORCHESTRATION
- Existing self-hosted n8n.
- n8n is NOT the real-time conversational backend.
- Use n8n for:
  - asynchronous orchestration;
  - scheduled jobs;
  - retries;
  - notifications;
  - post-call processing;
  - reporting;
  - campaign pacing;
  - missed-call recovery orchestration;
  - dormant reactivation;
  - exception/failure handling.

BOOKING
- Cal.com API v2.
- Prefer Cal.com Platform Starter for development/testing.
- Never design against API v1.
- Use a fictional 30-minute Meridian Discovery Consultation test event type.

TELEPHONY / SMS — LATER
- Twilio is introduced only after web voice + booking foundation is stable.
- Twilio should provide the Australian phone/SMS transport later.
- Australian SMS should use Twilio directly rather than Retell SMS.
- Do not require Twilio in Phases 1–5.

AI
- Retell handles real-time conversational AI.
- A direct LLM API may later be used for strict post-call structured extraction or free-form reply interpretation where justified.
- AI is never authoritative for critical lifecycle, eligibility, DND, duplicate, or booking truth.

FRONTEND
- Later operator interface may use Next.js/React if justified.
- UI must never become the authoritative business-logic layer.

CRM INTEGRATION
- Demo CRM is PostgreSQL first.
- Build a CRM adapter boundary so future integrations can support:
  - GoHighLevel;
  - HubSpot;
  - another CRM.
- Do not hard-code the system around one CRM vendor.

5. OPPORTUNITY LIFECYCLE STATE MACHINE
======================================================================

CANONICAL STATES

NEW
ENGAGED
QUALIFYING
QUALIFIED
BOOKING_READY
BOOKED
DORMANT
WON
LOST
CLOSED

PRIMARY PATH

NEW
→ ENGAGED
→ QUALIFYING
→ QUALIFIED
→ BOOKING_READY
→ BOOKED
→ WON

ALTERNATIVE PATHS

QUALIFYING → DORMANT
QUALIFYING → LOST

QUALIFIED → DORMANT

BOOKED → BOOKING_READY
only when booking is cancelled or requires rescheduling.

DORMANT → ENGAGED
only after a legitimate new interaction/reactivation.

Any active state → CLOSED
only through controlled deterministic/manual closure.

IMPORTANT:
- DND is NOT a lifecycle state.
- HUMAN_HANDOFF is NOT a lifecycle state.
- FOLLOW_UP_REQUIRED is NOT a lifecycle state.
- Human handoff is an ownership/escalation dimension.
- DND/contact eligibility is a channel-policy dimension.
- Follow-up is a next-action dimension.
- AI may recommend transitions.
- Application/backend rules validate and perform critical transitions.

Historical LOST opportunities should generally remain historical.
A genuinely renewed commercial enquiry should normally create a new linked opportunity rather than rewriting history.

======================================================================

CANONICAL STATES

PROPOSED
→ CREATE_PENDING
→ CONFIRMED

CONFIRMED → RESCHEDULE_PENDING → CONFIRMED
CONFIRMED → CANCEL_PENDING → CANCELLED
CONFIRMED → COMPLETED
CONFIRMED → NO_SHOW

CREATE_PENDING → CREATE_FAILED

RULE:
Checking availability does NOT reserve the slot.

Before booking:
- validate opportunity;
- validate contact requirements;
- validate eligibility;
- check duplicate/active booking;
- validate idempotency;
- handle slot conflict safely.

AI must never claim a booking succeeded unless backend/provider truth confirms it.

13. IDEMPOTENCY STRATEGY
======================================================================

Use multiple independent layers.

A. PROVIDER-EVENT IDEMPOTENCY
Unique key based on stable provider identifiers.

Concept:
provider + event_type + provider_event_key

Where provider event IDs are unavailable, derive a deterministic key from stable event fields.

B. TOOL-CALL IDEMPOTENCY
Store:
- provider_tool_call_id where available;
- idempotency_key;
- request_hash;
- prior outcome.

Same logical tool request should return the prior safe result rather than repeat the side effect.

C. DOMAIN IDEMPOTENCY
Examples:
- one active booking for one booking request;
- one active handoff for the same reason/call unless explicitly reopened;
- no duplicate prospect-context side effects.

D. EXTERNAL-PROVIDER IDEMPOTENCY
Before retrying booking creation:
1. inspect local booking attempt;
2. inspect known provider UID;
3. verify whether provider already created the booking;
4. retry only when safe.

- n8n downtime must not silently lose the provider event because the raw event has already been persisted.
- No lead/opportunity should silently disappear because one automation failed.

15. CONSENT / DND / CONTACT ELIGIBILITY
======================================================================

Contact eligibility is separate from opportunity lifecycle.

The system must answer, per channel/purpose:

- Can we respond inbound?
- Can we proactively call?
- Can we proactively SMS?
- Can we reactivate?
- Why?
- What provenance supports the answer?

Canonical eligibility result:

ELIGIBLE
REVIEW_REQUIRED
INELIGIBLE

Important:
- outbound_sms_eligible = false does not automatically mean inbound calls must be refused.
- explicit deterministic opt-outs must immediately stop future applicable outreach.
- AI may interpret ambiguous language.
- AI may never reverse a deterministic opt-out or DND decision.
- The portfolio should describe this as a technical eligibility control system, not claim it independently guarantees legal/regulatory compliance.
